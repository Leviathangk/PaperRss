# 发布流程与质量门禁

发布操作关系到线上版本分发与用户数据安全，必须严格执行全链路闭环与质量门禁。

## 发布全链路

- **版本规范**：遵守 SemVer（正式版 `vX.Y.Z`，预发布 `vX.Y.Z-beta.N`）。
- **全链路闭环**：发布需涵盖按 [分级验证矩阵](verification-matrix.md) 选定的必要自动化回归、候选产物构建与归档、真实交互验收、ChangeLog 记录、官网和 README 状态同步、Tag/Release 打标发布、线上分发及更新源验证闭环。发布授权不要求再次确认同一项操作。
- **构建入口**：`release.sh build` 执行 `verify.sh --all`；已覆盖且对应相同源码状态的 Core、Feature、Web 与宿主构建证据无需另行重复执行。可见窗口专项、手动像素诊断与真实交互不包含在该自动化门禁中。
- **更新通道**：Stable 与 Beta 两个 appcast 分别服务稳定通道与「Beta 通道（包含正式版）」；发布稳定版时必须同时刷新 `website/appcast/stable.xml` 与 `website/appcast/beta.xml`，否则 Beta 通道用户收不到正式版更新（`publish_release.sh` 已固化该行为）。

## Release 交互门禁（适用于 Beta 与稳定版）

- **真实交互验收**：发布候选版本必须先完成受影响路径的真实交互验收，再执行公开 Release、安装包上传与更新源切换。
- **证据关联**：记录源码状态（提交与本地改动）、候选版本 / Build、产物路径或摘要、验收环境与步骤。自动化回归证据须对应候选源码，交互验收须对应将发布的候选产物；同状态的有效证据可复用。
- **故障阻断机制**：交互发现明显错位、控件失效、内容缺失等问题时，立即中断发布流程并记录复现步骤。顺序固定为：修复 → 必要回归 → 构建新的候选产物 → 验收该产物 → 发布。构建或修改后不得继续沿用旧产物的交互证据。
- **门禁不可绕过**：
  - 已有发布授权、测试通过、构建或公证成功均不能替代交互通过。
  - 不得一边验收一边启动公开发布。
  - 不得把已发现的问题仅标注为已知问题后继续发布。
- **桌面影响**：真实交互优先使用经过验证的独立图形会话或虚拟机；`--isolated` 只隔离数据，不能作为不打断用户桌面的保证。签名、公证与存活冒烟均不代替交互门禁。
- **环境受限处理**：无法完成真实交互时，标记 `Manual UI verification required` 并保持发布中断，等待人工验收通过。

## Release 说明规范

1. **结构精简**：
   - 只保留「一句话发布概要（说明版本类型与升级建议）」与「更新要点（分类/分点列出解决的问题、优化与新功能）」。
   - 语言简练利落，不添加冗余营销套话。
2. **双语格式**：
   - 必须提供中英文两部分。
   - 上方为整块中文，中间以 `---` 分割，下方为整块英文。
